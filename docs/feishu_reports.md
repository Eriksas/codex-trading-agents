# 飞书日报：先讲清楚问题，再展示指标

## 这份日报回答什么

日报回答“冻结规则是否触发、观察记录有什么变化、数据是否足够解释”。策略长期是否有效，需要独立对照和后续样本；日报不承担这项证明。

统一按下面的顺序组织：

| 小节 | 应该写什么 |
|---|---|
| 今日结论 | 当前能确认的一句话；数据不齐时先说缺口 |
| 事实依据 | 数据日期、数量、比较对象和计数口径 |
| 如何理解 | 规则怎样作用于这些事实；不把设计意图说成已证明的效果 |
| 还不能判断 | 样本、覆盖、缺字段、相关与因果的边界 |
| 下一步 | 先修数据或按原协议继续记录，再做哪类验证 |
| 观察明细与来源 | 参数和辅助指标放后面，方便需要时核查 |

报告文字由 Python 按实际输入生成，无需新模型密钥，也不会为了增加“分析感”编造原因。

## 具体改进

- **目标比例与持仓分开。** G2/G3/G4 配上中文名称，说明比例是规则计算的目标，不是账户实际持仓。变化与上一条记录的明确日期比较，不将隔了几天的记录统称为“前日”。
- **事件数与股票数分开。** 同一反弹事件里的多只股票不扩大独立事件数量；模拟持有和等待入场分别计数。
- **百分数与百分点分开。** 合成示例中，五日跌幅 -1% 距 -5% 阈值差 4 个百分点；目标比例从 25% 到 50% 是增加 25 个百分点。
- **辅助指标与原因分开。** 转债低价券数量只描述既定筛选范围内的价格分布；没有分母就不算比例，不直接推出违约风险或 A 股涨跌。单日涨停数量也不写成明日方向预测。
- **规则过滤与因果分析分开。** V3 报告把过滤键翻译成中文，并注明按首个失败条件计数；某原因排除多少只，不等于该因素贡献了多少收益。
- **生成日期与数据日期分开。** 旧台账、不同日期和缺失指标明确标注；日期不一致先核对交易日历，不能只凭任务成功就说数据完整，也不能仅凭日期认定任务失败。

## 云端如何沿用

已核对仓库 Secrets 的名称和近期 Actions 状态，确认现有行情与飞书通道已配置，V3 日报和前向观察任务有成功记录。没有读取密钥值，也没有修改 Secrets。

两条既有调用路径保留：

- V3：`scripts/run_github_v3_daily_push.sh` → [scheduled_v3_reporter.py](../src/scheduled_v3_reporter.py) → notifier。
- 前向观察：原 Actions 调用 [forward_daily_report.py](../research/forward_daily_report.py)，默认仍输出 `/tmp/forward_daily_report.md`，随后以 full 模式推送。

新增了针对这两种报告的摘要提取，digest 模式也会保留结论、依据、局限与下一步，不再落入通用自选股摘要而丢掉分析内容。消息发送、认证、计划任务时间和策略计算均沿用原配置。

前向报告可用 `--state-dir`、`--date`、`--output` 只读生成预览。本轮测试通过本地飞书 post 内容转换检查最终段落，没有实际发送测试消息或触发定时任务。

## 面试时如何解释这份报告

可以这样说：“我先限定这份报告的问题：检查观察是否触发、规则输出怎样变化，以及数据有没有缺口。数值由程序读取台账汇总。接着区分事实和解释：比如目标比例上升只能说明规则输出变化，不能直接说明收益会改善。对于样本不足或缺少对照的部分，我明确不下结论，再写出下一项验证。这使报告既能支持日常检查，也能追溯每个判断的依据。”

这段话描述的是已实现的报告组织方法，不等于项目已经验证了稳定盈利。
